# MyApp.Repositories — Repository Blueprint

## Purpose ✅
This blueprint defines the standard conventions for repository projects in the solution. It explains folder layout, file naming, class/ interface patterns, EF configuration rules, DI registration, testing guidance, and example templates so future repository projects can be created consistently.

## Scope
- Applies to repository projects that implement data-access code for domain entities using EF Core.
- Does not prescribe business rules; repositories should expose data access methods only.

---

## Folder structure (standard)
- Root
  - `AppDbContext.cs` — application EF DbContext and helpers
  - `ServiceCollectionExtensions.cs` — DI registration extension method
  - `*.Repository.cs` — repository implementation files (one per repository)
  - `Configurations/` — EF IEntityTypeConfiguration<T> implementations (one per entity)
  - `Models/` — stubs or adaptation helpers for model types if required (prefer using shared `MyApp.Models` package)
  - `RepositoryBlueprint.md` — this blueprint & examples

Rationale: small, predictable layout makes finding repository and mapping code straightforward.

---

## Repository class conventions 🔧
- Location: project root (or `Repositories/` if many files).
- File name: `{Entity}Repository.cs`.
- Class name: `{Entity}Repository`.
- Namespace: `MyApp.Repositories`.
- Constructor: accept `AppDbContext` (and optional `ILogger<{Entity}Repository>` if logging needed).
- Interface: implement the corresponding interface defined in `MyApp.Interfaces.Repositories` (e.g., `ILeaseRepository`).

Method conventions (preferred standard API):
- List / query collections: `Task<IEnumerable<T>> ListAsync(CancellationToken cancellationToken = default)`
- Get by id: `Task<T?> GetByIdAsync(Guid id, CancellationToken cancellationToken = default)`
- Add: `Task AddAsync(T entity, CancellationToken cancellationToken = default)` (ensure entity Id set if empty)
- Update: `Task UpdateAsync(T entity, CancellationToken cancellationToken = default)`
- Delete: `Task<bool> DeleteAsync(Guid id, CancellationToken cancellationToken = default)` (return whether deleted)

Notes:
- Always include an optional `CancellationToken` on public async methods.
- Use `async/await` where you do multiple awaits or need try/catch; otherwise returning the Task from EF methods is acceptable.
- Repositories are responsible for persisting changes (call `SaveChangesAsync`) to keep current behavior — document if you later switch to Unit-of-Work pattern.
- Keep business logic out of repository; repositories may contain translation/flattening only for persistence concerns.

---

## Interface conventions
- Place interfaces in `MyApp.Interfaces.Repositories` (already part of solution).
- Name interfaces `I{Entity}Repository`.
- Match method names and signatures with the repository implementation.
- Keep interfaces small and focused to make mocking easy in tests.

---

## EF Configuration conventions 🧭
- Folder: `Configurations/`.
- File name: `{Entity}Configuration.cs`.
- Class name: `{Entity}Configuration` implementing `IEntityTypeConfiguration<{Entity}>`.
- Namespace: `MyApp.Repositories.Configurations`.
- Table naming: plural, snake_case (e.g., `leases`).
- Column naming: snake_case columns for Postgres compatibility; map model property names explicitly where the column name differs.
- Add indexes and relationships in configuration files; include comments for intended indexes.
- Keep configuration classes focused on mapping concerns only.

---

## DbContext conventions
- File: `AppDbContext.cs` in project root.
- Use `modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);` in `OnModelCreating`.
- Expose `DbSet<T>`s as read-only properties named as plural (`public DbSet<Lease> Leases => Set<Lease>();`).
- Include cross-cutting concerns (e.g., DateTime normalization) here with clear comments and tests.

---

## DI / Service registrations
- Provide a single method `IServiceCollection AddMyAppRepositories(this IServiceCollection services, IConfiguration configuration)` in `ServiceCollectionExtensions.cs` that:
  - Configures DbContext (Postgres vs SQLite detection) and retry policy.
  - Registers repository implementations as `AddScoped<I{Entity}Repository, {Entity}Repository>()`.
  - Registers `AppDbContext` for tests if needed.

Guidelines:
- Use `AddScoped` for repositories and `AppDbContext` (scoped per request).
- Keep registration ordered and grouped (e.g., auth, files, utilities) and add a single-line comment for groupings.
- Avoid fully-qualified interface registrations; add a `using` to top of file to keep registration lines concise.

---

## Error handling & transactions
- Repositories may throw EF exceptions; let higher-level services interpret and map to user-friendly errors.
- For multi-step persistence that must be atomic, perform transaction coordination at higher service layer OR expose a Unit-of-Work wrapper in the future.

---

## Testing guidance 🧪
- Unit tests: prefer using an in-memory or SQLite in-memory DB with migrations applied or use Microsoft.EntityFrameworkCore.InMemory for pure behavior tests.
- Integration tests: prefer using a disposable Postgres instance (e.g., Testcontainers) to ensure real behavior with migrations.
- Test naming: `{Entity}RepositoryTests` with methods `AddAsync_InsertsEntity`, `DeleteAsync_RemovesEntity_WhenExists`.
- Seed data via known helper fixtures and rollback DB between tests.

---

## Documentation & checklist ✅
When adding a new repository, ensure:
- [ ] Interface `I{Entity}Repository` added/updated in `MyApp.Interfaces.Repositories`.
- [ ] Implementation `{Entity}Repository` added in `MyApp.Repositories` and implements the interface.
- [ ] {Entity}Configuration added to `Configurations/` (if any DB mapping needed).
- [ ] DbSet<T> added to `AppDbContext` if the entity is new.
- [ ] DI registration added to `ServiceCollectionExtensions.cs` (grouped appropriately).
- [ ] Add unit/ integration tests.
- [ ] Update documentation and add example usage if needed.

## Examples / templates (copy-paste)

Repository template (C#):

```csharp
public class ExampleRepository : IExampleRepository
{
    private readonly AppDbContext _db;

    public ExampleRepository(AppDbContext db) => _db = db;

    public async Task<IEnumerable<Example>> ListAsync(CancellationToken cancellationToken = default)
        => await _db.Set<Example>().ToListAsync(cancellationToken);

    public Task<Example?> GetByIdAsync(Guid id, CancellationToken cancellationToken = default)
        => _db.Set<Example>().FirstOrDefaultAsync(e => e.Id == id, cancellationToken);

    public async Task AddAsync(Example example, CancellationToken cancellationToken = default)
    {
        if (example.Id == Guid.Empty) example.Id = Guid.NewGuid();
        await _db.Set<Example>().AddAsync(example, cancellationToken);
        await _db.SaveChangesAsync(cancellationToken);
    }

    public async Task UpdateAsync(Example example, CancellationToken cancellationToken = default)
    {
        _db.Set<Example>().Update(example);
        await _db.SaveChangesAsync(cancellationToken);
    }

    public async Task<bool> DeleteAsync(Guid id, CancellationToken cancellationToken = default)
    {
        var e = await _db.Set<Example>().FindAsync(new object[] { id }, cancellationToken);
        if (e is null) return false;
        _db.Set<Example>().Remove(e);
        await _db.SaveChangesAsync(cancellationToken);
        return true;
    }
}
```

Configuration template:

```csharp
public class ExampleConfiguration : IEntityTypeConfiguration<Example>
{
    public void Configure(EntityTypeBuilder<Example> builder)
    {
        builder.ToTable("examples");
        builder.Property(e => e.Id).HasColumnName("id");
        builder.Property(e => e.Name).HasColumnName("name");
        // TODO: add indexes, relationships
    }
}
```

DI registration snippet (in `ServiceCollectionExtensions.cs`):

```csharp
services.AddScoped<IExampleRepository, ExampleRepository>();
```

## Rationale & Tradeoffs 💡
- We keep repository methods persisting changes immediately to preserve existing behavior and minimize change impact across the codebase.
- An alternative is a Unit-of-Work pattern that centralizes SaveChanges; if the team prefers that, we should document the migration plan and update services accordingly.
